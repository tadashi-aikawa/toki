## タダシへの質問

- タダシの回答を待ってターンを終える質問は、平文・AskUserQuestionで出さず**質問票**で発行する。**複数案からの選択・採否・承認・GO/NO-GOを求める場合も含む**。単に調査結果や推奨案を報告し、判断を求めない場合は対象外。手順:
    1. `parliament ask --guide` で書き方を読む
    2. `parliament ask --draft` で一意な下書きファイルを作り、表示されたパスの雛形へ肉付けする(`/tmp/q.html` のような固定パスに自分で書かない。並行セッションと上書きし合う)
    3. `parliament ask <そのパス> [--task <タスクノート名>]` で発行する(parliamentに要操作表示され、回答は `<id>.answer.json` への保存とセッションへの1行注入で届く)
- 発行したら必ずターンを終える。発行できるのは**タダシと直接対話しているセッションだけ**(sub agent・委譲先は起動元経由)。回答を読んで用が済んだら `~/.parliament/questions/` の質問票一式を削除する
- タスクに紐づく質問は `--task` を必ず付け、発行・逆質問・再発行・回答の各イベントをそのタスクの経過欄へ1行(実時刻)+子項目で残す。票のJSONは削除し逆質問の本文はどこにも残らないので、経過欄が往復の唯一の正本
    - 発行: id・問いの要約・選択肢名 / 逆質問: 要旨 / 再発行: 旧id・新id・変更点 / 回答: 選んだ選択肢名+備考・全体補足の解釈(備考が本命の答えであることがある)。問いや選択肢の全文は書かない
- 例外: タダシとの対話が続いている最中の、直前の発言への即答想定の確認だけはそのまま聞いてよい。迷ったら質問票。`parliament ask` が失敗したら普通にターンを終えて聞く(縮退)

## parliamentのCodexセッション表示名

- rootセッションで最初の依頼の主題を理解したら、12〜28文字の簡潔な日本語タイトルを1つ作る
    - リポジトリ名だけ、または「調査」「実装」のような汎用名だけにはしない
    - セッション名は最初の主題で固定し、同じセッションでは以後の主題が変わっても上書きしない
- `parliament session-title report "<TITLE>"` を単独で1回実行する

    - 変数展開・パイプ・ifなどで包まない
- 現在ペインのCodex判定、session ID取得、mapping保存、herdr報告は専用コマンドが担う
- first-write-winsとし、同じsession IDでは1回だけ実行して既存名を上書きしない
- sub agentでは実行しない。現在ペインの取得は親ペインを返し、rootセッションの表示名を上書きするため
- herdr外やコマンドが失敗した場合は、Agent自身がherdr直呼びなどで報告を再構成せず、依頼を続行する

## Gitの取り扱い

- stage直前に `git status` を確認し、**このセッションで自分がEdit/Writeしていないファイル**があれば `git add -A` を使わず、自分が触ったパスだけ個別にstageする
- コミット直前に `git diff --cached` を通読し、**このセッションで自分がEdit/Writeしていない差分**が含まれていたらコミットせず、依頼元へ報告する
    - 同じリポジトリで複数のセッションが並行することがあり、他セッションの書きかけを巻き込むため
    - hunk単位の切り出しは試みない(`git add -p` は非対話環境では何もstageせず成功したように終わる)

## プロセスの停止

- **プロセスはポートかPIDで名指して止める**: `lsof -ti tcp:<ポート> | xargs kill`
    - `pkill -f` は使わない。ポートを環境変数で渡すサーバーは**コマンド行が完全に同一**になり、
      自分のプロセスと他人のプロセスをパターンでは原理的に区別できない

## 作業記録の日時管理

- 作業記録に日時を記載する前に `date '+%Y-%m-%dT%H:%M'` コマンドで現在時刻を確認する
- 作業開始時と完了時の時刻は論理的に整合性を保つ
- **禁止**: 未来の時刻や推測での時刻記載は絶対に行わない

## 情報収集と検証

- **AIツールの出力は必ず公式ソースで検証する**: GitHub Releases API・公式ブログ・CHANGELOG等で確認
- **GitHubリリース情報取得時**: `gh api repos/owner/repo/releases/tags/version` で `body` フィールドの詳細も必ず確認する
- GitHubに関することは `gh api` コマンドを極力使う
  - 読み取り系エンドポイント（一覧/詳細取得）で `gh api` に `-f` / `-F` を使う場合は、必ず `--method GET`（または `-X GET`）を明示する。
  - `gh api` は `-f` / `-F` 指定時に POST 扱いになるため、未明示だと意図せず作成APIを叩くことがある。
  - 例:
    - `gh api repos/{owner}/{repo}/issues --method GET -f state=closed -f per_page=100 --paginate`
- python, bash, node などを直接実行してJSONファイルを解析しない
  - 代わりに `jq` を使う

## 人間が読む文章の丸括弧補足

- 報告・文書など人- 報告・文書など人間が読む文章では、丸括弧の長い補足を構造へ逃がす。括弧内に読点・句点・リンクが入るなら括弧から出す
- 括弧に残してよいのは1語のタグ(実測/推定 等)と短い言い換えのみ。1語なら `理由:` のようなコード表記でもよい。1文に括弧1つまで、ネスト禁止
- 逃がし先は次の2つ。**脚注が使える媒体なら脚注を優先する**。本文の流れを切らずに逃がせるため
    - **脚注**: 時点・出典・長い補足に使う。使えるのはMarkdownドキュメントだけで、Slack・コミットメッセージ・ターミナルの報告文では使えない
    - **ネストした箇条書き**: 脚注が使えない媒体と、もともと箇条書きの中にある補足に使う。理由・条件・例外は行頭ラベル(`理由:` `例外:` 等)を付け、参照は「詳細: ...」の行を独立させる。複数あれば1リンク1行
- 同種項目の列挙も `/` 区切りで1行に連ねない。3個超か1項目が長い(全角20字超が目安)ならネストした箇条書きで1項目1行にする
